# Agent 设计说明

本文说明本项目的 Agent 如何分工、调度、调用工具并在中断后恢复。内容以 `src/ainovel` 当前代码为准。

## 1. 总体结构

系统将稳定的流程判断交给代码，将需要语义理解的决策交给裁定器，将开放式创作交给 Agent。

```text
入口 entry
  → 宿主与引擎 host
    → 状态加载与路由 flow
      → 创作代理 agents
        → 业务工具 tools
          → 文件存储 store

agents / arbiter
  → LLM 适配层 llm
    → LiteLLM
      → 模型供应商
```

Agent 不直接读写作品文件，也不直接决定整个工作流。每轮执行后，引擎重新加载已落盘状态，再计算下一步任务。

## 2. Agent 分工

项目包含五个 Worker 身份，其中规划师分为短篇和长篇两个版本。

| Agent | 主要工作 |
|---|---|
| `architect_short` | 生成短篇书籍信息、故事前提、扁平章节大纲和基础设定 |
| `architect_long` | 生成长篇分层大纲，展开后续弧，规划新卷或完本 |
| `character` | 创建角色档案，补齐缺失的角色设定 |
| `writer` | 制订章计划、起草或修改正文、一致性检查并提交章节 |
| `editor` | 完成全局或弧级审阅，生成弧摘要和卷摘要 |

代理定义集中在：

- `agents/catalog.py`：每个代理允许调用的工具和停止工具。
- `agents/workers.py`：组装提示词、工具、必需步骤和最大轮数。
- `agents/loop.py`：运行模型与工具调用循环。
- `agents/guard.py`：检查任务是否已经产生所需检查点。

## 3. 调度方式

调度采用“状态输入 → 纯函数路由 → 派发指令”的方式。

`flow/load.py` 先从作品目录读取进度、返工队列、设定缺项、弧卷边界、审阅状态和摘要状态，组装成 `RouteState`。`flow/route.py` 只根据该状态返回 `Instruction`，不读写文件，也不调用模型。

一条指令包含：

- `agent`：执行任务的代理；
- `duty`：本轮职责；
- `task`：发送给代理的任务文本；
- `chapter`：涉及的章节号；
- `reason`：派发原因。

主要路由顺序为：

1. 补齐书籍、前提、大纲或角色设定；
2. 处理返工与润色队列；
3. 重建缺失的审阅或摘要；
4. 处理影响后续剧情的大纲反馈；
5. 在弧末完成弧审阅、弧摘要和卷摘要；
6. 展开下一弧或规划新卷；
7. 执行到期的全局审阅；
8. 大纲用尽时决定扩展大纲或完本；
9. 其余情况写下一章。

非分层作品的全局审阅到期时，路由还可以同时提供“审阅”和“写下一章”两个候选任务，由计划调度选择执行顺序。

## 4. Agent 运行循环

`host/engine.py` 负责整本书的执行循环：

```text
加载状态
→ 计算或恢复派发指令
→ 检查用户放行与暂停条件
→ 运行指定 Agent
→ Agent 调用工具落盘
→ 检查职责是否完成
→ 重新加载状态并继续路由
```

Agent 循环只做三件事：

1. 将系统提示词、任务和工具定义发给模型；
2. 执行模型返回的工具调用，并把结果送回模型；
3. 在停止前检查本轮必需的检查点是否已经生成。

如果模型只输出文字、没有调用要求的落盘工具，检查点护栏会拒绝结束并要求继续。写作者必须完成章计划、正文、一致性检查和章节提交，审阅者必须保存对应的审阅或摘要结果。

## 5. 工具与权限

Agent 只能通过 `tools` 层操作作品：

- `tools/context.py`：读取设定、摘要、时间线和角色状态；
- `tools/foundation.py`：保存书籍信息、大纲、角色和世界设定；
- `tools/writing.py`：规划、起草、修改、检查和提交章节；
- `tools/review.py`：保存审阅、弧摘要和卷摘要。

不同 Agent 获得不同的工具集合。例如写作者不能修改大纲结构，审阅者不能提交正文。工具层负责校验参数、阶段和前置条件，避免模型越权或跳步。

## 6. 章节、弧和卷

- **章**是最小写作单元，包含章计划、草稿、正文和章摘要。提交时同步更新时间线、伏笔、人物关系和角色状态。
- **弧**由一组连续章节组成。弧末先审阅，再生成弧摘要和角色快照；下一弧尚未展开时交给长篇规划师细化。
- **卷**由多个弧组成。卷末生成卷摘要，再决定追加新卷、标记收官卷或完成全书。

短篇使用扁平章节大纲；长篇使用卷、弧、章分层大纲，只详细展开当前需要写作的弧。

## 7. 可恢复执行

系统不依赖模型对话恢复，而依赖文件事实：

- `meta/progress.json` 保存章节进度和返工队列；
- `meta/checkpoints.jsonl` 记录已经成功完成的步骤；
- 在途派单保存当前正在执行的任务；
- `meta/pending_commit.json` 保存冻结的章节提交意图。

章节提交采用分阶段流程：

```text
started
→ state_applied
→ progress_marked
→ signal_saved
→ 清理在途提交
```

提交前会冻结草稿和摘要、时间线、伏笔、关系、状态变化等参数。进程中断后从当前阶段继续，不使用模型重新生成参数；已经有正文、进度和提交检查点的章节直接返回既有结果。

## 8. 上下文与记忆

写作者上下文由以下内容组成：

- 最近章节摘要；
- 弧摘要和卷摘要；
- 时间线与伏笔记录；
- 角色快照；
- 当前章计划；
- 用户规则和相关历史章节。

摘要窗口和时间线窗口会随作品规模缩小。长篇启用卷、弧、章分层摘要。

对话超过预算后，`contextpack.py` 会依次省略旧工具结果、截断长消息、用文件摘要替换历史对话，必要时再调用模型生成压缩摘要。压缩后始终重新加入当前章计划和角色快照。

## 9. LiteLLM 适配

`llm` 层把不同模型供应商统一成同一种调用方式：

- `types.py` 定义模型、工具和补全结果；
- `litellm_client.py` 调用 LiteLLM 并接收流式输出；
- `stream.py` 聚合正文、推理内容和工具调用；
- `classify.py` 统一模型错误类型；
- `policy.py` 负责重试和备用模型切换。

超时或流中断时重试当前模型；限流或服务不可用时切换备用模型；鉴权失败或模型不存在时停止执行。

## 10. 用户干预与失败处理

不能由固定规则判断的情况交给 `arbiter` 生成结构化裁定，包括：

- 首次启动时选择规划方式；
- 用户提出修改、暂停或返工要求；
- 多个候选任务的执行计划；
- Agent 执行失败后的重试、改派或终止。

引擎还会记录相同“Agent + 任务”的重复次数。持续没有进展时先请求裁定，达到硬限制后暂停，避免无限循环。

## 11. 设计原则

1. 能由状态确定的流程使用代码路由，不消耗模型调用。
2. Agent 负责创作，不负责直接修改全局调度状态。
3. 所有重要结果必须通过工具落盘，不能只存在于模型回复中。
4. 检查点是步骤完成的依据，文件事实是恢复的依据。
5. 每轮重新加载状态，使中断恢复和重复执行保持一致。
6. 工具按角色隔离，流程由前置条件和检查点共同约束。
