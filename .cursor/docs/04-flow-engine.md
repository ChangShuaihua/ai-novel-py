# 路由与引擎循环

`flow.LoadState` 一次把路由需要的事实读齐。`flow.Route` 是纯函数：输入这份状态，输出一条指令或空。它不读文件，不调用模型，不写进度。

## 指令

```text
agent    architect_short | architect_long | writer | editor
task     交给该代理的任务文本
reason   为什么是这一步，写入事件和失败裁定
chapter  写作者涉及的章节号；规划师和审阅者没有章节时为 0
```

## 路由输入

状态里的字段必须显式列出。禁止在 `Route` 内部补读。

- `progress`
- `last_completed`：已完成章的最大号
- `arc_boundary`：上一章是否弧末，以及卷号、弧号、起止章、是否卷末、下一弧是否待展开、是否需要新卷
- `has_arc_review` / `has_arc_summary` / `has_volume_summary`
- `foundation_missing`：规划期还缺的设定项。短篇缺 `outline.json`。进度标明分层，或已经有非空的 `layered_outline.json` 时，改查分层大纲和指南针，不再把扁平 `outline.json` 当成缺项
- `planning_tier`
- `has_global_review`：非分层书在审阅到期点，该章是否已有 `scope=global` 的审阅。分层书恒为假
- `immediate_feedback_count`：必须在续写前处理的外部修订条数。写作者的普通反馈不在这里，留到下一次自然的结构操作
- `aggregate_refresh`：外部修订后最早一个要重建的弧审阅、弧摘要、卷摘要或全局审阅

## 决策顺序

互斥，从上到下命中第一条：

1. 没有进度，或阶段是 `complete`：返回空。完本总结由宿主按文件渲染，不再调用模型。
2. 阶段还不是 `writing`：设定有缺项且 `planning_tier` 已有值，派对应规划师补齐。缺项只有 `foundation_audit` 时，任务改为重读工件并调用 `audit_foundation`。级别还是空：返回空，交给引擎做启动补裁。
3. `pending_rewrites` 非空：派写作者处理队首。流程是 `polishing` 则任务用“打磨”，否则用“重写”。
4. 流程是 `reviewing` 或 `steering`：返回空。审阅和干预不由查表抢跑。
5. `aggregate_refresh` 有值：派审阅者重建对应工件。
6. `immediate_feedback_count` 大于 0：派当前规划师，只处理这批外部修订，然后结束。
7. 分层书并且上一章是弧末，按缺口顺序派发：弧审阅 → 弧摘要 →（卷末）卷摘要 → 下一弧仍是骨架则 `expand_next_arc` → 需要新卷则让长篇规划师三选一：继续追加卷、追加并标记收官卷、或 `complete_book`。
8. 非分层书，已完成章数到达全局审阅间隔，且该书还没有这次全局审阅：派审阅者，`scope=global`。
9. 非分层书，下一章号大于 `total_chapters`：派规划师决定完本，或从下一章续接大纲。禁止派写作者去写大纲里不存在的章。
10. 其他：派写作者写 `NextChapter`。

弧末三连（审阅、弧摘要、卷摘要）齐了，收官卷才允许自动完本。未宣告收官的书，完本还要求伏笔和长线归零，这个判断在设定工具里做，不在 `Route` 里做文学评估。

## 引擎循环

单线程串行。取消上下文等于暂停，检查点保证已落盘的步骤不丢。继续和进程重启都是起一个新循环，不恢复模型对话。

每一轮：

```text
排空已排队的干预控制动作
章节推进门处理边界（消费一次性暂停、核对放行许可）
指令 = 干预派单 或 Route(LoadState) 或 规划期补裁
指令为空 → 退出循环
前置检查
章节推进门是否放行这条指令
僵局计数
运行对应代理
按错误分类决定重试、裁定或暂停
预算与推进政策在边界上再生效
```

控制状态只在循环边界改。干预里的暂停、重开、派单排队到边界再提交；先建好返工事实，再允许推进门消费暂停。回答用户和写入规则可以马上做。

### 前置检查

- 阶段已是 `complete`：丢掉派发。
- 写作者的目标章在分层大纲里还是骨架、尚未展开：不跑写作者，改派 `architect_long` 做 `expand_next_arc`。这是确定性改派，不用模型判断。

### 规划期补裁

`start_prompt` 先落盘。启动裁定成功后，`plan_start` 再落盘，然后才按裁定派规划师。

崩溃恢复时：

- 裁定已经在 `run.json` 里：按这份记录续派，不重新问模型。
- 用户需求在，但裁定从未成功：现场补裁一次。这是首次裁定的重试。补裁失败就暂停并说明，禁止静默停机。

### 僵局

每轮记下 `agent + task`。上一轮执行后查表仍得到同一键，计数加一。指令变了就清零。代理内部新的 plan、draft、edit 检查点不算引擎级进展。

- 计数到 3：把事实交给 `deadlock` 裁定。裁定说重试时不清零。
- 计数到 5：暂停并通知。确定性引擎必须有这个上限。

### 失败

- 模型层可重试的错误在代理循环内消化，引擎看不到。
- 确定性错误（未知代理、工具参数在代码层就不可能合法）：暂停。
- 其余代理错误：同一指令再跑一次。仍失败则 `worker_failure` 裁定，动作为 `retry`、`reroute` 或 `abort`。
- 裁定自己失败，或动作是 `abort`：暂停并通知。

裁定产生的派单在执行前对账。对账字段是阶段、流程、返工队首。检查点序号只记审计，不对账：干预发生时代理可能还在跑，序号一定会变。对不上就丢掉这条派单，把原始干预送回完整裁定路径重问。

### 结束

循环结束时按文件定终态：

- 阶段是 `complete`：标记完成，并用已有摘要、角色、伏笔和字数渲染完本报告。不再为报告调用模型。
- 其他：空闲或已暂停。

这里禁止任何“再启动引擎”的调用。

## 启动、恢复、干预

### 新建

```text
用户需求
  → 进度初始化，检查点重置
  → start_prompt 写入 run.json
  → plan_start 裁定（选规划师，过短的需求在任务文本里补全）
  → 裁定写入 plan_start，并追加 decisions.jsonl
  → 引擎按这条指令启动
```

裁定失败不是死局：需求已经在文件里，下次恢复会补裁。

### 恢复

没有会话要恢复。进程起来后：

1. 做一致性告警（例如进度说第 N 章已完成，但 `chapters/NN.md` 缺失或为空）。告警不自动改文件。
2. 推进门对账。
3. 若 `pending_steer` 存在，先走干预裁定，再拉起引擎。
4. 否则引擎以空指令启动，完全由 `Route` 从文件重算。

重复派发安全，因为写工具按检查点幂等，未完成的提交按 Saga 续跑。

### 干预

`steer` 与用户在停机时发出的继续，都走同一条裁定路径：

```text
先把 pending_steer 落盘
  → 收集事实 → 裁定
  → 追加 decisions.jsonl
  → answer 回显；rules 立即写入本书规则
  → hold / reopen / dispatch 进入边界队列
  → 全部成功后清除 pending_steer
```

第一次写 `pending_steer` 如果失败，就停止，绝不在没有恢复记录时继续执行。引擎停着的时候，边界动作立即执行，并按意图决定要不要拉起循环。

仍有两个不保证的窗口：派单已经进内存队列时进程被硬杀，以及并发输入还在等锁。用户在场可以重发，成本是再裁定一次。

长效写作要求走 `rules`，归一化进 `meta/user_rules.json`，由 `novel_context` 注入。改篇幅和后续剧情走派给规划师的 `dispatch`。改旧章走审阅入队或 `reopen`。
